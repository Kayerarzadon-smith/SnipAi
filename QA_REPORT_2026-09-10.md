## Findings

### F1 — `verify_removals.py` measures the wrong audio · P2 · new

`level()` in `ugc-edit-system/tools/verify_removals.py` puts `-ss` **before**
`-i`. Its docstring argues for that placement. On this footage it lands late,
and not by a little.

Measured: six 80ms windows immediately before an EDL piece boundary, each one
read twice — once by that tool's own method, once by slicing the decoded
source by sample index.

| window | sample-exact mean | what `-ss` reports | error |
|---|---|---|---|
| 88.627–88.707 (img-9817) | −77.4 dB | −24.8 dB | **+52.6** |
| 94.708–94.788 (img-9817) | −77.4 dB | −24.5 dB | **+52.9** |
| 81.614–81.694 (img-9817) | −76.0 dB | −36.9 dB | +39.1 |
| 35.484–35.564 (img-9823) | −77.5 dB | −22.3 dB | **+55.2** |
| 56.902–56.982 (img-9823) | −77.4 dB | −26.1 dB | +51.3 |
| 61.370–61.450 (img-9823) | −74.9 dB | −45.8 dB | +29.1 |

The seek lands roughly 85ms late, so on a fragment of a few tens of
milliseconds the tool measures *different audio entirely*. Half the sampled
windows were wrong by 30–55 dB — wider than the 8 dB margin the whole check
turns on.

Why this one matters more than its size suggests: the spec tells the tester to
run this tool on the app's single worst failure mode and **"Report what it
says, not what the timestamps imply."** A removal that really does carry
speech can be measured in the silence after it and pass. And it manufactures
defects in the other direction too — my own first pass, using the same method,
flagged three fragments on img-9823 as speech; all three were silence, and all
three disappeared under exact measurement.

`qa/BUGS.md` already records `-ss`-before-`-i` as an instrument error made
twice in ad-hoc measurement. It is still in the production tool.

**Fix:** decode the source audio once and slice it, or select the window with
`-af atrim` rather than a per-fragment seek.

**Its verdict was right this time.** Re-measured exactly: 0 of 13 interior
removals on img-9817 and 0 of 32 on img-9823 carry speech.

### F2 — `verify_removals.py` never looks at a beat's edges · P3 · new

It inspects only the gaps *between* pieces of a beat — the interior holes. The
in-point and out-point are where `snap()` works, and the only clipping this
project has actually shipped was there: the "s" of *this*, the "ce" of *face*
(`10ab9c3`). The instrument that caught those was `qa/verify_words.py
--against`, which needs an older build to compare with. There is no absolute
edge check at all, and `verify_words` labels its own absolute count an upper
bound — correctly, since Whisper starts words early.

So the class of defect BUG-001 was about is invisible to the tool the spec
points the tester at.

`qa/verify_edges.py` (attached) closes that: for every spoken word only partly
rendered, it measures the **unrendered** part against the project's own speech
level, sample-exact. It found the two documented consonants on img-9817
without being told about them, which is the check working.

### F3 — both built cuts predate the word-protection fix, and nothing says so · P3 · new

img-9817's EDL totals **97.618s** — the pre-fix number `10ab9c3` records
("cut 97.62s → 100.66s"). Sample-exact measurement of the v6 file on disk:

| beat | word | dropped | level | floor |
|---|---|---|---|---|
| `under-eyes-looks` | `this,` | 26ms at the out-point | −22.5 dB mean, −12.4 peak | −26.2 dB |
| `egf-going-improve` | `face.` | 21ms at the out-point | −22.9 dB mean, −11.6 peak | −26.2 dB |

Those are the two clipped consonants the fix was written to remove, still
present in the file the Queue offers. `WORD_RESCUE` would catch both on a
rebuild (boundary inside a short word, nudge ≤0.2s). img-9823's EDL is from
00:29 PDT; the fix landed 13:13 PDT, so it is stale the same way.

The app tracks whether a render matches the *edit* (`86a90d4`) but has no
notion that the *pipeline* changed underneath an existing build. Two
consequences: a tester following the spec measures these and files a bug that
is already fixed, and you could post a file carrying clipping the code no
longer produces.

**Not a cutting bug — a staleness-signalling gap.** A pipeline version stamped
into `work/edl.json` and compared on load would cover it.

### F4 — the spec's top-priority check decodes 4K video to measure audio · P3 · new

`silent_stretches()` and `black_frames()` in `qa/verify_media.py` pass the cut
to ffmpeg with no stream selection, so measuring *audio* fully decodes a
2160×3840 h264 file. Extracting the audio of img-9817-v6 takes **1.9s**;
running silencedetect over the same file as written does not finish inside
180s. `-vn -map 0:a:0` on the silence pass is the whole fix.

This is why the check Part 6 ranks first is the one a tester is most likely to
abandon.

---

### F5 — learning writes into the app bundle on a fresh library · P3 · new-ish

`_paths.py:data_path()` documents a copy-on-write — *"copied into the library
the first time anything writes to it"* — and there is no copy anywhere in the
file. So when the library has no `state/tuning.json` yet, `data_path` returns
the copy beside the code and `learn_from_edits.save()` writes **there**:
inside `SnipAi.app/Contents/Resources/pipeline/state/`. Every learned
correction is then lost on the next `./scripts/bundle-app`, the library never
gains the file, and it keeps writing into the bundle forever. Read-only once
the app is signed (B2), it fails outright instead.

Adjacent to LEDGER **P13**, which is about `--apply` *dying* on a fresh
library; this is about where it writes when it doesn't die. Either the
docstring's copy-on-write should exist, or writers should resolve against
`data_root()` directly rather than through `data_path()`.

## Part 6 #1 — do the finished videos actually play correctly?

Yes. Both cuts, measured rather than trusted:

| | img-9817-v6 | img-9823-v2 |
|---|---|---|
| format | 2160×3840, 30fps | 2160×3840, 30fps |
| video / audio stream length | 98.367s / 98.373s | 178.900s / 178.908s |
| A/V delta | **5ms** | **8ms** |
| EDL total | 97.618s (47 pieces) | 177.303s (93 pieces) |
| drift vs EDL | 749ms, allowance 1567ms — **pass** | 1597ms, allowance 3100ms — **pass** |
| longest silent stretch (−50dB, ≥1.5s) | **none** | **none** |
| interior removals carrying speech | **0 of 13** | **0 of 32** |
| EDL pieces outside the source | 0 of 47 (source 526.66s) | 0 of 93 (source 651.03s) |
| inverted or empty pieces | 0 | 0 |

The dead-air work (BUG-007, BUG-009) holds: zero silent stretches on either
cut. Two edge fragments on img-9823 looked like dropped words and are not —
`good-thing-medicube` ("good thing that MediCube has a, I") and `no-guess`
("No, I guess, I") are abandoned takes, and the audio past their out-points is
the first word of the *next* attempt. Dropping it is take selection working.
Recorded here because the timestamps say otherwise and the next tester will
see the same thing.

**Black frames at the joins: NOT TESTED.** Decoding 4K portrait h264 runs
about 9 fps in this sandbox against a 180s ceiling per command; a 98s cut needs
~350s of decode and a 179s cut twice that. Worth one run on your Mac, where it
is minutes rather than impossible — and faster still once F4 is fixed.
